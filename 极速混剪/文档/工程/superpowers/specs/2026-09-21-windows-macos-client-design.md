# 极速 VideoMix Windows 与 macOS 双平台客户端设计

日期：2026-09-21
状态：已确认
适用范围：桌面客户端、授权校验、本地处理后端、客户端更新与发布流程

## 1. 背景与目标

当前产品由 Electron 桌面客户端、Vue 3 渲染界面、Windows C# 启动与授权代理、Python 打包的本地处理后端，以及 PHP/MySQL 授权服务器组成。现有正式交付物只支持 Windows，客户端开发方式主要是在已有 `app.asar` 上重建补丁，项目中缺少完整的 Electron/Vue 源码和部分 Windows 构建源码。

本次工作的目标是建立可持续维护的 Windows 与 macOS 双平台版本：

- 两个平台共用同一套 Electron/Vue 客户端核心和业务行为。
- 每次客户端功能更新默认同时评估、实现和验证 Windows 与 macOS。
- 保留现有 Windows 用户的授权绑定，升级后不应无故占用新设备名额。
- macOS 使用稳定、可解释、可解绑的设备身份。
- 授权服务器能够针对不同平台和 CPU 架构发布正确的更新包。
- Windows 与 macOS 的正式安装包均经过平台要求的签名；macOS 还必须经过 Apple 公证。
- 视频处理继续在用户本机执行，不将素材默认上传到云端。

首期目标平台为：

- Windows x64
- macOS Apple Silicon（arm64）
- macOS Intel（x64）

首期不制作 macOS Universal 安装包。arm64 和 x64 分开交付，可以减小包体，也能更早发现平台依赖问题。

## 2. 已确认的现状与约束

### 2.1 客户端

- Electron 主进程入口为 `dist-electron/main.js`，渲染层位于 `dist/`。
- 渲染层使用 Vue 3、Pinia、Vue Router 和 Element Plus。
- `app.asar` 中未发现 `.node`、`.dll`、`.dylib` 或 `.so` 原生模块，界面层具备直接跨平台复用的基础。
- Electron 主进程已经包含 `darwin` 分支、macOS 更新器和无 `.exe` 后缀的后端候选路径，说明原程序曾考虑跨平台运行。
- 当前 ASAR 内没有源映射，且工作区没有完整的原始 Electron/Vue 工程。因此不应继续把二进制补丁作为长期双平台开发方式。

### 2.2 本地处理后端

- 当前交付物是 Windows 的 `KrLongAI.exe`，其 `_internal` 目录包含 Windows Python 3.11、PySide6、pywin32、Playwright Chrome、FFmpeg/ffprobe/ffplay 等资源。
- 主进程已按平台寻找 `backend` 或 `KrLongAI`，并在非 Windows 平台补充可执行权限。
- Windows 后端不能复制到 macOS 直接运行。macOS 必须从后端源码分别构建 arm64 和 x64 产物，并替换 Windows 专用库与资源。
- 如果无法获得 `KrLongAI.exe` 对应的完整 Python 源码，必须先恢复或重建后端实现。反编译后的二进制内容不能成为正式、长期维护的代码基础。

### 2.3 授权与更新

- PHP 授权服务目前把设备 ID 当作普通字符串比较，接口注释中的 `category` 尚未参与授权逻辑。
- 授权票据由服务器使用 RSA 私钥签发，客户端可使用公钥离线验证；此格式可以跨平台复用。
- 当前更新服务只保存一份 `client_update_*` 文件信息，不能同时发布 Windows、macOS arm64 和 macOS x64。
- 当前 Windows C# 启动器承担本地授权代理等职责，macOS 无法使用该启动器。

## 3. 方案选择

采用“共享 Electron 客户端 + 平台专属处理后端 + 统一授权和发布协议”的方案。

不采用以下方案：

- 不把完整 Python 处理后端重写成 Node.js。重写范围过大，容易造成处理结果不一致。
- 不把 macOS 处理默认迁移到云端。该方案会改变成本、隐私和离线使用模型。
- 不维护两套独立客户端。双份界面和业务逻辑会快速产生功能差异，也违背后续同步更新要求。

## 4. 总体架构

```text
                    HTTPS
  Windows 客户端  ----------\
  Electron + Vue             >  PHP 授权与更新服务 + MySQL
  Windows 后端    ----------/

  macOS 客户端    ----------\
  Electron + Vue             >  同一套授权、票据与更新协议
  macOS 后端      ----------/
```

Electron 主进程负责跨平台桌面能力：窗口、IPC、授权代理、设备身份、票据存储、后端生命周期和更新。Vue 渲染层只通过受控 IPC 或现有本地 API 使用这些能力，不直接读取系统标识、私钥或执行文件。

处理后端保持同一份业务源码，按平台和架构构建为独立 sidecar：

- `win32-x64/backend.exe`
- `darwin-arm64/backend`
- `darwin-x64/backend`

Electron 包只携带当前目标对应的 sidecar 和运行资源，不在单个安装包内混装所有平台文件。

## 5. 源码恢复与工程基线

双平台开发开始前，建立新的可构建源码工程，而不是继续仅修改 ASAR：

1. 恢复或取得 Electron 主进程、preload、Vue 渲染层和 Python 后端的原始源码。
2. 以当前正式 Windows 版本作为行为基线，对页面、IPC、处理任务和授权流程建立回归测试。
3. 对不能恢复的界面模块，可根据当前 ASAR 行为逐步重建，但必须在源码工程中形成可维护实现。
4. 保留现有 ASAR 重建工具，仅用于旧 Windows 版本的紧急修补，不作为新版本主构建链。
5. 将 Electron、Vue、Python 后端、PHP 服务端协议和构建配置纳入版本控制。

后端源码可用性是首个硬性里程碑。未取得或重建后端源码前，只能完成 macOS 客户端壳、授权和更新框架，不能宣称 macOS 功能版完成。

## 6. 授权设计

### 6.1 本地授权代理

将当前 Windows C# 启动器中的 `127.0.0.1:8081` 授权代理迁入 Electron 主进程，保持现有渲染层调用契约，减少界面改动。

代理必须：

- 只监听回环地址，不对局域网开放。
- 在启动时检查端口冲突，并产生可诊断但不包含激活码的日志。
- 对请求方法、路径、请求体大小和字段做白名单校验。
- 统一转发至 HTTPS 授权服务器，并设置连接与响应超时。
- 在退出时停止监听并清理资源。
- 不在日志中写入完整激活码、完整票据或设备原始标识。

C# 启动器在迁移期保留兼容作用；当 Electron 内置代理在 Windows 验证稳定后，再从正式安装链中移除 C# 授权职责。

### 6.2 设备身份

服务端保存的设备 ID 使用版本化格式：

```text
vm-device-v2:<platform>:<sha256-derived-id>
```

原始系统标识只在本机用于派生摘要，不上传服务器。派生输入包含应用命名空间、平台标识和稳定系统 ID，并通过 SHA-256 生成不可逆标识。

平台规则：

- Windows：优先保留当前已发布版本的设备 ID 算法。升级后的同一台 Windows 设备必须继续得到旧 ID，避免重新绑定。只有首次安装且无历史身份时，才采用 v2 格式。
- macOS：使用稳定的系统级标识派生设备 ID，不使用用户名、主机名、IP 地址或可移动磁盘序列号。
- Intel Mac 与 Apple Silicon Mac 使用相同格式；设备身份不应因应用升级或 Rosetta/原生运行方式变化而改变。
- 操作系统重装、主板更换或迁移到另一台电脑可能产生新设备 ID，用户通过后台解绑旧设备处理。

### 6.3 授权名额与跨平台规则

Windows 和 macOS 视为不同设备。一个激活码能否同时绑定两台设备，由现有设备数量限制决定，不因平台自动增加名额。

示例：只允许一台设备的激活码已经绑定 Windows，用户改用 Mac 时，需要先在管理后台解绑 Windows，再在 Mac 激活。此规则与现有授权模型一致，也避免平台切换绕过设备数限制。

服务端扩展设备记录，新增 `platform`、`arch`、`client_version` 和 `device_id_version`。这些字段用于后台显示、诊断和迁移，不改变设备名额计算的基本规则。

### 6.4 票据存储与离线校验

- 保持现有 RSA 密钥体系和票据签名算法，避免无必要的密钥迁移。
- 票据继续绑定激活码、设备 ID 和有效期。
- Windows 历史票据继续兼容读取。
- 新版本的敏感本地状态使用操作系统安全存储：Windows Credential Manager/DPAPI，macOS Keychain。
- 网络不可用时，仅在票据签名、设备绑定和有效期均通过时允许离线使用。
- 服务端返回设备不匹配时，客户端继续显示已确认文案：`当前激活码与设备不匹配，请重新输入`。

## 7. 本地处理后端设计

### 7.1 共享协议

Electron 与处理后端之间保持统一协议和端口策略，平台差异封装在 sidecar 启动层。后端必须提供：

- 健康检查与版本信息。
- 任务创建、进度、取消和结果查询。
- 能力信息，包括当前平台、架构、FFmpeg 版本和可用功能。
- 明确的错误代码，避免界面依赖平台特有错误文本。

Electron 启动后端时验证文件存在、执行权限、版本兼容性和健康状态。异常退出应有限次数重启，超过阈值后向用户显示可理解的错误，不进入无限重启。

### 7.2 macOS 适配清单

必须逐项处理：

- 移除或替换 pywin32、Pythonwin、Windows 注册表和 Win32 GUI 调用。
- 使用 macOS 对应的 Python、PySide6、NumPy、Pillow、cryptography 等架构产物。
- 分别携带 arm64 与 x64 FFmpeg/ffprobe；FFmpeg 的编解码器能力在两个架构上保持一致。
- Playwright/Chrome 若确有业务用途，按平台获取 Chromium；若仅用于遗留功能，应先确认是否可以移除，避免显著增加安装包体积。
- 路径处理使用跨平台路径 API，不假设盘符、反斜杠或 Windows 字体目录。
- 临时文件和日志写入应用数据目录，不写入签名后的 `.app` 包内部。
- 对 sidecar、动态库和内嵌工具执行完整代码签名，并在公证前验证签名链。

### 7.3 一致性要求

相同输入、模板和参数在 Windows 与 macOS 上应产生业务上等价的输出。允许因编解码器和浮点实现出现不可避免的字节级差异，但以下结果必须一致：

- 分辨率、帧率、时长和音轨布局。
- 字幕内容、时间轴和字体回退规则。
- 转场、裁剪、缩放和混合参数。
- 任务状态、进度语义和错误分类。

## 8. 更新协议与后台改造

### 8.1 查询协议

客户端检查更新时明确提交：

- `platform`: `win32` 或 `darwin`
- `arch`: `x64` 或 `arm64`
- `version`: 当前客户端版本
- `channel`: 首期固定为 `stable`

更新服务按 `platform + arch + channel` 选择发布记录。旧 Windows 客户端没有这些参数时，服务端继续返回现有 Windows x64 更新，保证向后兼容。

### 8.2 数据模型

将单组 `client_update_*` 设置迁移为更新发布表，每个产物至少保存：

- 版本、渠道、平台、架构
- 文件名、下载地址、字节数、SHA-256
- 应用级 RSA 签名
- 是否强制更新、发布说明、发布时间
- 下载次数和启用状态

唯一约束为 `version + channel + platform + arch`。后台一次发布可以关联多个平台产物，并显示哪些目标尚未上传或验证。

### 8.3 完整性与平台签名

保留现有应用级 RSA 更新签名，同时增加平台签名验证：

- 下载后先验证长度、SHA-256 和 RSA 签名。
- Windows 安装包必须通过 Windows 代码签名。
- macOS 应用、sidecar 和 DMG/ZIP 更新内容必须使用 Developer ID 签名并通过 Apple 公证。
- 任一校验失败均不得安装，错误日志只记录摘要和错误类别。

更新元数据和安装包必须使用 HTTPS。不得使用相同版本号覆盖已发布文件；修复发布必须递增版本。

## 9. 构建、签名与发布

### 9.1 构建环境

- Windows x64 产物在 Windows 构建机或 Windows CI runner 上生成。
- macOS arm64 和 x64 产物在 macOS 构建机或 macOS CI runner 上生成。
- 当前 Windows 电脑不能生成可正式签名并公证的 macOS 发布包。
- macOS 正式发布需要 Apple Developer Program 账号、Developer ID Application 证书、Team ID 和公证凭据。
- Windows 正式发布需要可信的代码签名证书或云签名服务。

### 9.2 产物

每个正式版本至少包含：

- Windows x64：NSIS 安装包及更新元数据。
- macOS arm64：DMG 安装包、ZIP 更新包及更新元数据。
- macOS x64：DMG 安装包、ZIP 更新包及更新元数据。
- 每个文件的 SHA-256、应用级 RSA 签名和发布说明。

### 9.3 同步发布门禁

从双平台版本进入正式发布后，任何客户端改动默认同时适用于 Windows 和 macOS。发布流程必须满足：

1. 共享代码测试通过。
2. Windows x64 冒烟与处理回归通过。
3. macOS arm64 冒烟与处理回归通过。
4. macOS x64 冒烟与处理回归通过，至少由真实 Intel Mac 或受支持的 Intel macOS runner 验证。
5. 三个平台产物完成签名与校验，macOS 完成公证和 stapling。
6. 更新后台的三个目标均已上传且版本一致。
7. 先发布内部验证渠道，完成升级与回滚测试后再启用 stable。

若某项功能确实无法在某平台实现，必须在需求阶段明确记录并经产品确认；不能在发布时临时省略某个平台。

## 10. 错误处理与用户体验

- 授权服务不可用：区分网络错误、服务器错误和票据失效；存在有效离线票据时允许进入。
- 设备不匹配：清除无效会话并提示用户重新输入，不自动占用新名额。
- 后端缺失或签名失败：阻止处理任务，提示重新安装，不静默下载未签名程序。
- 后端启动失败：展示诊断编号，日志记录平台、架构、版本和退出码，不记录用户素材内容。
- 更新不适配当前平台：视为无可用更新，不下载其他平台包。
- 强制更新：只有目标平台存在通过验证的产物时才生效，避免用户被锁死在无法更新的状态。

## 11. 测试策略

### 11.1 自动化测试

- 设备 ID：稳定性、版本迁移、Windows 旧 ID 兼容、macOS Rosetta/原生一致性。
- 授权代理：激活、校验、超时、离线票据、无效签名、设备不匹配和端口冲突。
- 更新选择：旧 Windows 无参数请求、三种目标组合、错误架构、签名错误和强制更新保护。
- sidecar 管理：路径选择、权限修复、健康检查、崩溃恢复和版本不兼容。
- 处理协议：任务创建、进度、取消、失败和结果解析。
- PHP 数据迁移：现有设备记录和单一 Windows 更新记录迁移后仍可读取。

### 11.2 平台验证矩阵

每个平台至少验证：首次安装、覆盖升级、授权激活、离线启动、主题持久化、素材导入、完整处理任务、取消任务、导出、自动更新和卸载重装。

处理回归使用一组固定素材，覆盖常见视频、音频、字幕、中文字体、长路径和非 ASCII 文件名。测试比较输出元数据和关键帧/音频特征，不要求跨平台文件哈希完全相同。

## 12. 迁移与交付阶段

### 阶段一：建立源码与测试基线

- 找回或重建完整 Electron/Vue 源码。
- 找回或重建 Python 后端源码。
- 将当前 Windows 1.0.3 的关键行为固化为回归测试。
- 建立版本控制和可重复的 Windows 构建。

完成标准：可从源码生成行为与当前正式版一致的 Windows 测试包。

### 阶段二：授权与更新跨平台化

- 将授权代理迁入 Electron。
- 实现版本化设备 ID 和安全票据存储。
- 扩展 PHP 设备字段与更新发布模型。
- 保持旧 Windows 客户端和旧设备绑定兼容。

完成标准：新旧 Windows 客户端均能正常授权和检查更新，macOS 客户端壳能完成激活与离线校验。

### 阶段三：macOS 处理后端

- 清理 Windows 专用依赖。
- 构建 macOS arm64/x64 sidecar 和媒体工具。
- 完成处理一致性测试和包体优化。

完成标准：两种 Mac 架构均通过固定素材处理回归。

### 阶段四：签名、公证与同步发布

- 配置 Windows 签名、macOS Developer ID 签名和公证。
- 建立多平台构建与发布流程。
- 验证首次安装、升级、强制更新保护和回滚流程。

完成标准：同一版本号的三个正式产物均通过发布门禁，可由后台按平台正确分发。

## 13. 验收标准

本项目满足以下条件时视为双平台能力完成：

- Windows 现有授权用户升级后无需重新占用设备名额。
- macOS arm64 和 x64 均可安装、激活、离线启动并完成完整视频处理任务。
- Windows 与 macOS 使用同一套界面与业务源码，没有长期维护的功能分叉。
- 授权后台能显示设备平台和架构，并能解绑任一设备。
- 更新服务不会向客户端返回错误平台或错误架构的包。
- 三个平台均完成签名验证，macOS 通过 Gatekeeper 与 Apple 公证检查。
- 自动化测试和固定素材回归通过。
- 发布清单明确记录 Windows 与 macOS 同步交付状态。

## 14. 已知外部依赖与阻塞条件

- 需要取得或重建 `KrLongAI.exe` 对应的 Python 后端源码。
- 需要一台可用于构建和验证的 Mac，或可用的 macOS CI runner。
- 正式分发前需要 Apple Developer Program 凭据和 Windows 签名能力。
- 当前目录不是 Git 仓库；进入实现阶段前应建立正式源码仓库，以便审查、回滚和同步发布。

这些条件不会阻止先完成源码审计、协议设计和 Windows 兼容工作，但会阻止正式 macOS 功能版签名发布。
